# Ativação do Harness em 05/08/2026

Runbook para ativar o pipeline autônomo do VibeChat. A configuração e o
Readiness são feitos uma vez; depois do `PASS`, o ciclo opera 24/7 sem aprovação
humana por run. É o go-live dos agentes, não um deploy do produto em produção.

## Resultado esperado

Ao final da ativação:

- ambiente Cloud inicia sem `task dev`;
- preflight produz um veredito reproduzível;
- schedules de Build, UX, Watchdog e Retrospective estão ativos;
- Build inicia por `SEC-RLS-RUNTIME`;
- Security e QA revisam cada `head_sha`;
- nenhum merge de código ocorre sem evidência durável e required check;
- auto-merge por squash está ativo e protegido pelos gates;
- Docs fecha o item após merge;
- Watchdog recupera falhas determinísticas;
- PR Repair corrige reprovações/CI no mesmo PR e devolve um novo SHA aos
  checkers;
- a Retrospective acumula evidência para análise humana posterior;
- um run futuro consegue retomar somente com repo, PRs, checks e lease.

## 1. Preparação única — antes de habilitar escrita

No dashboard Cursor:

- manter Build, Docs e recovery com escrita desabilitados;
- criar/sincronizar **0) Readiness / Preflight** com
  `.cursor/automations/00-readiness.prompt.md`;
- sincronizar os prompts 01–08 com os arquivos versionados;
- configurar Security em PR ready/synchronize;
- configurar QA no mesmo evento;
- configurar Watchdog em modo read-only;
- configurar Retrospective semanal;
- configurar PR Repair nos eventos de review/workflow failure;
- deixar concorrência Build = 1.

No GitHub:

- exigir `Build & test`, gitleaks e dependency audit;
- instalar e validar `VibeChat Security Review`;
- torná-lo required check antes de auto-merge;
- conceder ao QA somente os scopes necessários para comentário/aprovação;
- habilitar `Allow auto-merge` e squash;
- manter environments/secrets de produção fora do token.

Build/Docs/recovery e os schedules permanecem desligados somente durante esta
preparação. Isso evita merge desprotegido antes de os controles externos
existirem; não cria uma etapa de supervisão recorrente.

## 2. Preflight somente leitura

Executar manualmente a automação 0. Ela deve:

1. executar `task agent:check`;
2. validar `docker info` após `agent-setup.sh`;
3. validar Compose sem subir o produto inteiro;
4. verificar main, PRs duplicados e checks;
5. verificar branch protection e permissões;
6. reportar `PASS`, `BLOCKED` ou `UNKNOWN` por gate.

Critério:

- `PASS` permite ligar schedules e auto-merge protegido;
- `UNKNOWN` em prompt sync, required check ou permissão mantém escrita e merge
  desligados durante a preparação;
- `BLOCKED` precisa de correção antes do Build.

## 3. Ativação autônoma

Após `PASS`, habilitar:

1. Build a cada 2 h, concorrência 1;
2. Security Review e QA por PR ready/synchronize;
3. auto-merge por squash, condicionado a todos os required checks;
4. Docs / Close por merge em `main`;
5. Watchdog horário;
6. UX Review diário;
7. Harness Retrospective semanal.
8. PR Repair em reprovação do QA, review acionável ou workflow failure.

Não há aprovação humana entre essas etapas. Branch protection, QA, Security,
checks e o recheck do `head_sha` fornecem o controle independente. O humano
analisa depois os PRs, runs, retrospectivas e métricas; só uma condição R4 exige
intervenção.

O Build deve selecionar `SEC-RLS-RUNTIME`, porque a safety lane Critical precede
B-104 e qualquer feature. Se selecionar outro item, interromper o run: a seleção
está errada.

O trabalho RLS só passa se provar, entre outros critérios:

- role runtime não owner, superuser ou `BYPASSRLS`;
- `FORCE ROW LEVEL SECURITY` + `WITH CHECK`;
- API/Worker usando a credencial runtime;
- testes SELECT/INSERT/UPDATE/DELETE cross-tenant com essa credencial;
- migration/backup separados e rollback/roll-forward documentado.

## 4. Estado operacional

| Estado | Condição | Configuração |
|--------|----------|-------------|
| Setup | Readiness `BLOCKED`/`UNKNOWN` | Escrita e auto-merge desligados |
| 24/7 | Readiness `PASS` | Build 2 h; UX diário; Watchdog horário; Retrospective semanal; auto-merge protegido |
| Degraded | Falha isolada ou check indisponível | PR Repair/Watchdog recupera; PR afetado não mergeia e trilhas independentes seguem |
| Safety stop | Main vermelho, secret ou cross-tenant | Cancelar auto-merge afetado; hotfix/revert; revalidar antes de retomar |

Concorrência Build começa em 1. Só pode aumentar mediante lease compartilhado
atômico comprovado; frequência e concorrência não mudam no mesmo dia.

## 5. Painel mínimo diário

O resumo do Watchdog deve permitir responder:

- `main` está verde?
- qual Work-Item está ativo?
- existe PR duplicado ou lease stale?
- qual SHA foi revisado?
- quais checks ainda bloqueiam?
- qual foi o stop reason do último Build?
- houve no-progress, retry repetido ou custo anômalo?
- há ação R4 envelhecendo?

Métrica sem decisão associada é ruído. Cada alerta deve apontar para “pausar”,
“corrigir”, “esperar” ou “seguir”.

## Kill switch e rollback automáticos

Se houver vazamento cross-tenant, secret, merge incorreto, loop repetitivo ou
custo anômalo:

1. o required check impede novos merges do SHA afetado;
2. o Watchdog cancela o auto-merge dos PRs afetados quando tiver permissão;
3. novos merges da trilha ficam bloqueados por finding/check conclusivo;
4. PRs, logs, SHAs e leases são preservados;
5. nenhuma branch ou volume é apagado para “limpar”;
6. o Watchdog abre hotfix/revert conforme `operacao-24x7.md`;
7. após a correção, Security e QA revalidam o novo SHA e o fluxo retoma.

Se a plataforma não permitir ao Watchdog cancelar auto-merge, o required check
continua sendo a barreira primária e a falta de permissão vira ação externa
durável. O agente não pede supervisão a cada run.

## Checklist de aceite do dia

- [ ] `task agent:check` passa;
- [ ] Cloud Agent inicia e `docker info` responde;
- [ ] prompts 00–08 foram sincronizados;
- [ ] Build concorrência 1;
- [ ] schedules Build/UX/Watchdog/Retrospective estão ativos;
- [ ] Security publica check durável no SHA;
- [ ] QA publica veredito durável;
- [ ] required checks bloqueiam merge;
- [ ] `Allow auto-merge` por squash está habilitado;
- [ ] primeiro Work-Item é `SEC-RLS-RUNTIME`;
- [ ] nenhum secret/produção/R4 foi usado;
- [ ] `RUN_RESULT` possui stop reason e próxima ação;
- [ ] Watchdog reporta o estado e só cria recovery determinístico;
- [ ] Retrospective semanal registra saúde e melhoria recorrente elegível;
- [ ] PR Repair atualiza o mesmo PR e nunca aprova/mergeia a própria correção.
